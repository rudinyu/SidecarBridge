# ScreenDock 1.5 (123)

## Product and upstream integration

- Build separate ScreenDock Host and ScreenDock Viewer apps from `project.fork.yml`. Keep the author's `project.yml` and checked-in Xcode project at the upstream baseline.
- Isolate ScreenDock app identifiers, saved settings, pairing credentials, and received files from SidecarBridge. ScreenDock requires its own first pairing and macOS permissions.
- Preserve the SidecarBridge iPhone/iPad protocol and six-field pairing QR format. The Host advertises both products' discovery services; ScreenDock Viewer browses the ScreenDock services.
- Prefer TCP 45454. Use 45455 when the original Host is running or 45454 is occupied. Moving the listener leaves accepted connections under their existing session owner.

## Viewer and Host behavior

- Remove persistent full-screen overlay buttons. Use the View menu or Control-Command-H for controls, and native full screen or Control-Command-F to leave full screen.
- Minimize the Host's own main window after the Viewer reports its first visible image.
- Keep the authenticated Viewer's input surface available before the first video frame and during video recovery. Input remains disabled until the Host explicitly grants remote-input permission.
- Route text for secure or unknown focused fields through keyboard events, without placing it on the Host clipboard.
- Report authenticated remote activity to macOS so the display can wake. This does not unlock the user's session.
- Recover from capture start failures, a missing first encoded frame, sustained unavailable capture status, and a capture refresh that does not complete. Retries are bounded, and stale callbacks cannot replace a newer capture generation.
- Separate source-state counters, encoded-frame progress, and the Viewer's presentation acknowledgement in the Host diagnostic report.

## Locked-session scope

The intended scenario is an already logged-in macOS user whose screen is locked.
The user still enters their macOS password to unlock it. This release does not
add pre-login, logged-out, restart, or FileVault access.

Actual lock-screen capture and input must be checked on the target Host. A
successful build or an input acknowledgement does not establish that macOS
displayed a lock-screen frame or accepted the input.

## Physical acceptance

1. Pair ScreenDock Viewer with ScreenDock Host while the Host is unlocked and confirm moving video and remote input.
2. Lock the Host while connected. Check that the link remains usable and that the lock screen can be displayed.
3. Disconnect the Viewer, leave the Host locked, and reconnect using the saved pairing.
4. Click the remote password field and enter the password manually. Confirm that desktop video resumes after unlock.
5. Repeat after display sleep and confirm that retries stop after disconnecting.

Record the Host macOS version and capture-stage diagnostics if any step fails.
Do not include passwords, pairing codes, clipboard contents, or private keys in
the report.
